# 游戏文案部（游戏内文案多语言）

管游戏里每一句面向玩家的文字：UI 按钮、道具名、对白、提示语。
和文档翻译部的分工：**文档翻译部管"给人读的整篇文档"**（README/商店页/patch notes），
**游戏文案部管"游戏里的一条条短文案"**。术语表两边共用（见下）。

参考脚本：`scripts/commands/game-i18n.js`（零依赖）· 配置：`game-i18n-manifest.json`

## 各引擎一般什么样（问诊科普用）

| 引擎 | 惯例做法 | 词典长相 | 本房间怎么配合 |
|------|---------|---------|--------------|
| Godot | 内置支持，官方推荐 CSV，代码用 `tr("KEY")` | CSV | 词典格式选 csv，translationMarks 填 `tr(` |
| Unity | 官方 Localization 包（String Tables）；小项目常自造 JSON 字典 | 引擎资产或 JSON | 自造 JSON 就全功能；用官方包则只用 scan + glossary |
| Ren'Py（视觉小说） | 内置最省心，一条命令自动抽对白生成翻译文件 | 自有 .rpy 格式 | 词典引擎托管，只用 scan + glossary |
| RPG Maker | 默认不支持，靠社区插件 | 看插件，多为 JSON/CSV | 按插件的词典格式配 |
| Unreal | 内置 Localization Dashboard，FText 自动收集 | 引擎管 | 词典引擎托管，只用 scan + glossary |
| HTML/JS 自造 | 没有标准，各家自己写字典 | 通常 JSON | 全功能，格式选 json-per-lang 或 json-single |

规律：词典格式落到纯文本就两大类——JSON 和 CSV，脚本都支持；
引擎全托管的（Ren'Py/Unreal），词典不归这管，但**硬编码扫描和术语表照样有用**。

## 建房间问诊（三连问）

1. **有多语言计划吗？** 目前考虑到哪一步？
   - 明确要做 → 继续问下去
   - 没有/没想好 → **不建房间**，但留一句忠告：文案尽量别散着写死在代码里，集中放
     ——哪怕暂时只有中文。以后想翻时是搬家一天搞定，还是全仓考古三星期，就看这个
2. **游戏内现在有多语言机制吗？**
   - 已有 → 盘点接上：词典什么格式、在哪、翻译函数叫什么。**绝不推倒重来**
   - 没有 → 按引擎给推荐默认值（上表）
3. **什么引擎/技术栈？** 决定词典推荐格式和扫描规则（目录、后缀、注释风格）

问诊结果写进 `game-i18n-manifest.json`（模板见 templates/game-i18n-manifest.template.json）。

## 四个机制

### scan · 硬编码扫描

揪出散在代码里、没进词典的裸文案——这些文字外语玩家永远看不懂。
- 逐行找字符串字面量里的中日韩文字（注释先剥掉，不误报）
- 行里出现翻译函数标志（`t(`、`tr(` 等，manifest 里配）→ 已收编，放过
- 带词边界判断：配了 `t(` 时，`alert(` 结尾的 `t(` 不算数
- 日志/调试/开发工具这类"本来就不用翻"的路径 → 加进 `scan.skip`
- 有命中 exit 1，可挂 CI 防新增

### coverage · 覆盖率

以源语言词典为基准算差集：`en 缺 37 条`，进度条一目了然。`--missing` 列清单。

### stamp + drift · 记指纹与漂移检测

和文档翻译部同一个思想，粒度到每条文案：
- 翻完某语言跑 `stamp en`——给每条译文记下"基于当前这版源文案翻的"（内容指纹）
- 源文案一改指纹就对不上，`drift` 点名：`ui.start → en 过期（原文改过）`
- 这解决 coverage 看不出来的问题：**key 都在，但内容已经是旧的**
- `drift --check` 给 CI/发版前用，有过期就 exit 1

指纹库 `game-i18n-state.json` 进 git。

### glossary · 术语表（全项目共用）

**术语表的本质是"这个游戏的自造词典"**——每个游戏都有自己的黑话：
你的游戏里行动资源可能不叫体力、叫"灵魂"，那全游戏、商店页、patch notes、
所有语言里它就只能是"灵魂"。翻译一致性只是它的第二功能，
第一功能是给所有人（**尤其是 AI**）立规矩。

```json
{
  "terms": [
    {
      "zh": "灵魂",
      "meaning": "行动资源，出击消耗（类似别家游戏的体力/耐力）",
      "en": "Soul",
      "ja": "ソウル",
      "note": "世界观设定：人物靠灵魂驱动，刻意不用通用词"
    }
  ]
}
```

- 语言码字段 = 该语言的唯一标准叫法；`meaning` 用类比讲清"这是什么"——
  不懂这个游戏的人（和 AI）靠它入门黑话，理解了自然不会误用
- `glossary lint`：扫全词典，源文案含术语的，译文必须用标准译法，抓出
  "灵魂一会儿 Soul 一会儿 energy"
- `glossary check --lang en --source "<原文>" --text "<译文>"`：翻单句时随手核对
- **一份 glossary.json 全项目共用**：游戏文案部和文档翻译部都查它，
  游戏内、商店页、patch notes 三处才能互相一致

## AI 日常纪律

- **写任何面向玩家的文字之前，先查术语表**——游戏文案、商店页、patch notes、
  成就名，全算。用这个游戏自己的叫法，不用通用词
- 新造了术语（起了个新叫法）→ 顺手登记进 glossary.json，别让它口口相传
- 写代码时文案直接进词典，不写死在代码里；干完活跑 `scan` 保持零硬编码
- 改了源语言文案 → 跑 `drift` 看哪些译文过期，补翻后重新 `stamp`
- 发版前体检：`scan` + `drift --check` + `glossary lint` 三连
- 翻译完译文，先跑 `glossary check` 再交稿

## 建房间流程

1. 问诊三连（上面）→ `init` 生成 manifest 草稿 → 按实情改
2. 已有词典的旧房改造：格式对上后先跑 `coverage` 看现状，
   再和用户确认哪些译文当前和原文对得上 → 逐语言 `stamp` 记指纹（同文档翻译部的旧房纪律：
   把过期译文错误地记成 fresh 是唯一自己救不回来的错误）
3. 术语表从 templates/glossary.template.json 起步，和用户一起把游戏现有黑话都登记进去
